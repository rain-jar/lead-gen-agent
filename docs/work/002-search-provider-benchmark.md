## Outcome

Compare Exa, Brave Search API, and Serper on the same frozen query set and benchmark, then recommend a primary and fallback search provider with case-level evidence, measured latency, and actual or dated estimated cost. If the evidence does not distinguish them, report that instead of naming a winner.

## Recommendation and reason

Use **frozen benchmark v2** as the primary known-item set. It covers 14 eligible editions, 12 Canadian, across more event types; v1 has four eligible editions and all seven founder positives are from one U.S. edition. Preserve v1 as a continuity check, without pooling its cases into v2 scores. Report live and replay results separately. A replay result measures whether an existing evidence page can be retrieved now, not what a historical index returned or what a live user can find today.

Revision 2 keeps that recommendation and changes only the frozen query design, locale pinning, recall reporting, adjudication method, and spending cap, as specified in Amendment A.

## Scope

1. Implement a small common search-result format (query, provider, rank, title, URL, snippet if supplied, timestamp, latency, error and reported cost) and minimal Exa, Brave and Serper adapters. Do not build the application discovery pipeline yet.
2. Use the frozen provider-independent query matrix in `docs/benchmark/search-provider/queries-v1.tsv`. It contains **58 queries per provider**, generated by the rule in "Frozen query design" below. The same 58 strings run in the same order for every provider, with a top-10 result cutoff and no benchmark names, domains, person names or event URLs in queries.
3. Save raw ranked responses and run metadata, then score offline against frozen v2. Keep manual URL-to-edition adjudications and newly found qualifying editions in separate records; do not change v2 ground truth during the run. Pool and judge unique URLs once across providers (see Comparison and scoring).

Out of scope for this run, and deferred to a later approved round if needed: a provider-native query mode (for example Exa's recommended natural-language style), and a second full live run or a repeat of the live comparison on a later date.

### Frozen query design

Each English query is the plain-space concatenation of one geography, one intent, and the single time phrase, in that order. Each French query uses the same pattern with the French place, intent, and time phrases. No provider-specific query syntax, site restriction, date filter or semantic rewrite is used in this first comparison. The exact strings generated from these terms (Appendix A) must be saved and checksum-recorded before calling any provider.

Generation rule, in this order:

1. Walk the 13 geographies in the run order below.
2. For each geography, emit the four English intents in the order below, using the English place string and the English time phrase.
3. After the English block for `Montreal` and for `Quebec City` only, emit the three French intents in the order below, using the French place form and the French time phrase.

This produces 52 English queries and 6 French queries, **58 per provider**. The frozen TSV has SHA-256 `7cc841763f57a56850194a706702ea1d670a43fc7fdcb4813cafd445ded78c1f`; any change to its strings or the US$5 cap requires Raj's OK before use.

| Dimension | Fixed phrases |
| --- | --- |
| Intent, English (4) | `startup pitch competition finalists`; `startup accelerator demo day founders`; `university entrepreneurship pitch showcase`; `entrepreneurship competition finalists` |
| Geography (13), in run order | `Canada`; `Montreal`; `Quebec City`; `Toronto`; `Ottawa`; `Hamilton`; `Waterloo`; `Calgary`; `Edmonton`; `Saskatoon`; `Vancouver`; `Halifax`; `United States` |
| Time, English (1) | `upcoming 2026 2027` |
| Intent, French (3), Montréal and Québec City only | `concours de pitch startup`; `demo day entrepreneurs`; `concours entrepreneuriat finalistes` |
| French place forms | `Montréal`; `Ville de Québec` |
| Time, French (1) | `à venir 2026 2027` |

The national `Canada` query gives every Canadian edition a country-level route. Each other Canadian string is a single city, so keyword and semantic engines see a comparable query. `United States` is last, matching the Canada-first product direction. There is one U.S. scope, not U.S. city scopes.

The fourth English intent is a generic, inclusive phrase. It exists because v2 includes social-venture, Indigenous (SOAR), and other non-tech cases that the three original tech-startup intents may miss.

A single time mode is used. The earlier second mode, `2026 finalists`, is dropped. Replay scores already must not be presented as what a live user would find, and `upcoming 2026 2027` still retrieves 2026 announcement pages for offline replay scoring. Dropping the second mode keeps the per-provider budget modest after adding cities, the inclusive intent, and the French family.

English queries use the common unaccented web-search forms `Montreal` and `Quebec City`. French queries use `Montréal` and `Ville de Québec` (`Ville de Québec` is unambiguous; `Québec` alone can mean the province).

Geography notes, from frozen v2, so known-item expectations stay honest:

- Eligible v2 cities covered by a dedicated scope: Montréal (3 eligible editions), Calgary (2), Ottawa (2), Toronto (1), Vancouver (1), Halifax (1), Saskatoon (1), Hamilton (1, McMaster replay). The two U.S. eligible editions (Hen Hatch, live; San Diego Founders Fight Club, replay) depend on the `United States` scope plus any incidental hits.
- `Hamilton` is in the list because v2 has an eligible replay edition there, with three verified founder cases.
- `Waterloo`, `Edmonton`, and `Quebec City` are Canada-first coverage scopes, not known-item denominators. Waterloo appears in v2 only as a past, ineligible edition (Velocity Pitch Competition 2026). Edmonton and Québec City have no v2 opportunities. Hits from those scopes may contribute to new-discovery or trap-exposure counts, not to known-event recall denominators.

This matrix is a recommendation, not a product query strategy. Remaining likely weaknesses — one U.S. scope rather than city scopes, no provider-native syntax, and limited known-item support outside the cities above — must be reported, not silently tuned away after results.

## Comparison and scoring

- Query budget: 58 initial calls per provider; at most one retry for a transient failure, recorded separately. Request up to 10 ranked results per query. If a provider cannot return 10, retain the actual result count and report the difference.
- Run providers in rotating order by query to reduce time/order effects. Apply the pinned locale table above. Document unavailable or provider-specific controls that cannot be equalized.
- Deduplicate results by `edition_key` within each split. A source counts for known-event recall@10 only when it is an official/event page for the eligible edition. An evidence-page hit is scored separately for founder/organizer cases. Preserve every missed case and adjudication reason.
- Report **both** known-event recall views:
  - **Run-level union recall@10** (primary known-event figure): an eligible edition is found if an official or event source for that `edition_key` appears in the top 10 of any query in the frozen set, divided by eligible editions in scope. This answers whether the provider can find the edition at all under the budget.
  - **Per-query recall@10** and **mean official/event hits per query**: how often a given in-scope edition appears in a single query's top 10, and the average number of distinct in-scope official/event editions in a query's top 10. Also report these by intent family and by geography.
- Also report evidence-page recall@10, judged precision/relevance@10, trap exposure, duplicates, independently verified new discoveries, latency and cost as defined in the v2 README. Break out live/replay and Canada/U.S.; show opportunity type where the denominator permits.
- Lead the written report with a per-edition × provider hit matrix for all 14 eligible editions (template in Appendix B). State the small-n caveat in the report: v2 has 8 live eligible editions, so one hit or miss moves live recall by 12.5 points (1/8). Live Canadian recall uses 7 editions, so one event is about 14.3 points. Do not name a winner when the difference is one or two editions; call that comparison inconclusive.
- Before judging precision or relevance, pool result URLs across all three providers and deduplicate them. Record the normalization rule (at least scheme, host case, and trailing slash). Judge each unique URL once against the recorded rubric, then score every provider against that shared pool. Keep the adjudication log reviewable. Unjudged results are never credited as relevant.
- Prioritize **live Canadian eligible-edition recall**, then live overall recall and precision, then replay diagnostics, new discoveries, latency and cost when recommending a provider. No fixed winner threshold is claimed. Because v2 has no live Canadian founder positives, do not infer live Canadian founder yield from these results; weekly held-out sets will test that later.

## Security Impact

The three API keys are read only from the ignored local `.env`; `.env.example` and `.gitignore` were already committed before implementation. No key values are printed or saved. The runner redacts any accidental key occurrence in serialized provider responses, verifies HTTPS certificates against the operating-system CA bundle, and counts every attempt against the US$5 cap. Local run artifacts and the installed vendor skill are gitignored. No deployment or remote write is part of this slice.

## Risks and reversal

V2 has limited live founder coverage (the only live founder positives are U.S., from Hen Hatch) and its replay split is not historical index replay. The 58-query design may still favour some wording or regions; a later comparison may use a newly approved query revision, but all providers must be rerun under that same revision. Locale parameters can drift as APIs change; the freeze-time verification step is required for that reason. The adapters and local artifacts can be replaced without changing product data or a production system.
